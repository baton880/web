# Журнал заданий погрузчика

> Актуально на 2 октября 2026: production-хранилище заданий — PostgreSQL; подтверждённые шаги сразу участвуют в realtime-замесе и независимо сверяются с HOST/GPS. SQLite больше не является production backend.

Сервер выдаёт фиксированный план выбранной группы и принимает последовательные подтверждения оператора. Например: выдача плана → begin с исходным весом → confirm каждого компонента → completed. Изменение рациона после выдачи не меняет уже выданное задание.

## API и расчёт

Все маршруты `/api/loader` используют существующую авторизацию сайта. ADMIN и DIRECTOR ведут задания. Оператор видит свои задания; ADMIN может читать все. GUEST не может создавать задания или события.

- `GET /groups`: только группы с активным рационом. Неактивные рационы и связанные группы не показываются и не допускают выдачу нового задания. Нет корректного плана у активного рациона — `plan: null`.
- `POST /tasks`: `{id, deviceId, groupId, planRevision}`. UUID обеспечивает повторяемую выдачу; изменение исходного плана возвращает 409. Один Хозяин имеет не более одного ready/active задания.
- `GET /tasks?deviceId=...`: последние 50 доступных заданий.
- `GET /tasks/active?deviceId=...`: незавершённое задание.
- `GET /tasks/:id`: снимок и журнал событий.
- `POST /tasks/:id/events`: `{id, type, revision, at, stepIndex, reading}`; отмена вместо reading содержит reason.

План использует существующий `module-2/calculatePlan`: норма на голову, количество голов, кормлений в день и порядок компонентов. Цели округляются до 5 кг. Составной компонент — заранее приготовленная смесь: он остаётся одним шагом под своим именем и с общей массой. Внутренние ингредиенты комбикорма не выдаются погрузчику как отдельные загрузки. SHA-256 снимка служит planRevision.

## События и сохранность

`begin` фиксирует исходный вес. `confirm` сохраняет прирост, конечное измерение, время и переводит на следующий компонент; последнее подтверждение завершает задание. `undo` отменяет только последнее подтверждение, пока последующий вес не изменился более чем на 5 кг. `cancel` сохраняет причину и закрывает незавершённое задание.

Измерение должно содержать deviceId задания, valid=true, конечный числовой weightKg, исходный timestampMs в пределах 5 секунд от времени события. Сервер проверяет ожидаемую revision, порядок времени и допустимость перехода. Задержанная отправка допустима: оценивается время нажатия, не время доставки. Один UUID с тем же содержимым подтверждается повторно без второй записи; другое содержимое с тем же UUID получает 409. Событие и состояние сохраняются одной PostgreSQL-транзакцией.

Production использует таблицы `LoaderTask`, `LoaderTaskEvent` и `LoaderTerminal` в общей farm DB. PostgreSQL-адаптер блокирует задание при изменении revision и сохраняет событие с обновлённым состоянием атомарно. SQLite-реализация сохранена только для совместимых тестовых фикстур и старых архивов; новые production backup получают эти таблицы единым PostgreSQL snapshot.

## Установка и проверка

Маршруты подключены в `server/src/index.js`; production выбирает `PostgresLoaderTaskStore` при `INGRESS_BACKEND=postgres`. Перед обновлением применяются PostgreSQL migrations и генерируются Prisma-клиенты по `docs/server-platform/OPERATIONS.md`.

Перед обновлением сохранить текущий commit, приватную конфигурацию и проверенный PostgreSQL backup. Новый release готовить отдельно, не редактируя рабочий каталог на месте. После проверки синтаксиса выполнить из корня:

```
node server/scripts/loader-tasks-test.mjs
```

Тест создаёт отдельный временный журнал и проверяет расчёт, составные компоненты, неизменность плана, разрешения, дубли, undo, атомарный отказ, повторное открытие БД и HTTP API.

После перезапуска проверить `/api/health`, существующий telemetry current, авторизованные `/api/loader/groups` и `/api/loader/tasks/active`. При выключенных весах группы и выдача задания доступны; для событий загрузки нужен свежий вес. Для отката восстановить предыдущий код и сохранённые серверные правки, перезапустить процесс; журнал сохранить.

## Связь с realtime-замесом

`begin` открывает независимое причинное окно проверки, `confirm` сразу сохраняет планшетный факт в `BatchIngredient`. Алгоритм получает вес только из HOST-пакетов; `reading.weightKg` служит планшетным фактом и не подменяет независимый расчёт. При согласии в настроенный допуск рабочим весом становится `algorithmWeight`, исходный планшетный `actualWeight` сохраняется отдельно. GPS сначала определяет компонент; только для неоднозначной пары солома/люцерна планшет может выступить подсказкой с низкой уверенностью.

События планшета не запускают replay и не переписывают raw `Telemetry`/`RtkTelemetry`. Realtime-замес восстанавливает незавершённое состояние из `AppState`. Старый postprocess используется для legacy-истории и непостоянного admin preview, но не заменяет сохранённые realtime-факты.

На графике деталей замеса показываются обе временные границы по `event.at`: начало `begin` и конец `confirm`. Если у фактов есть `tabletTaskId`, отображаются только события связанных заданий; временной fallback применяется лишь к старой истории.

Код Android-приложения и тест управления планшетом в этот серверный коммит не входят.

Уже выданный снимок не переписывается при отключении рациона или изменении правил расчёта. Для нового представления плана старое незавершённое задание можно отменить и получить заново.

Регистрация терминалов без суточного истечения JWT описана в [loader-terminals.md](loader-terminals.md). Для терминала доступ к заданиям ограничен владельцем и закреплённым Хозяином, включая терминалы администратора. Для обычного входа сайта существующие права сохраняются.
