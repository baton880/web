# Серверный выпуск with-tablet

Ветка основана на `refactor/server-platform-postgres`, commit `54ab8bc`, и
предназначена для уже перенесённого PostgreSQL-сервера. Она не является обновлением
старого SQLite production. Дополнительной миграции БД эта функция не требует.
Production обновлён 26.09.2026; подробности и проверки ниже.

## Что изменено

- `/api/loader/groups` выдаёт зарегистрированным планшетам `plan.offlineToken`:
  подписанный сервером неизменяемый план, связанный с владельцем, terminalId и
  deviceId. Вход для первой регистрации и первой загрузки каталога нужен онлайн.
- `/api/loader/tasks` принимает этот токен вместе с обычными id, deviceId,
  groupId, planRevision. Старый выданный план допустим после изменения/удаления
  рациона. Доверие не распространяется на произвольный JSON от клиента.
- Токен не имеет срока истечения: это осознанная поддержка последнего известного
  рациона без интернета. Отозванный терминал всё равно не проходит авторизацию API.
  Изменение ключа подписи делает старые автономные планы непринимаемыми; ключ
  сохранять при обновлениях и backup. Не ротировать при неотправленных заданиях.
- События replay остаются последовательными, UUID-идемпотентными, с проверкой
  ревизии. На одном Хозяине сервер по-прежнему допускает одно активное задание.
  Конфликт не перезаписывает журнал и не создаёт молча другое задание.
- `/api/loader/weight` возвращает `scaleMeasurement`, если rawPayload содержит
  валидную структуру `scale_measurement` от новой Pi. Вес не проходит серверную
  фильтрацию/тарирование, время и packetId не обновляются при HTTP-чтении.
  Путь для старой Pi сохраняет старый ответ. Новый планшет различает эти случаи.
- `calibrationId` сохраняется в baseline/end событий и проверяется при
  подтверждении/возврате. Калибровка посреди задания требует сверки.

## Подготовка и установка

1. Сделать и проверить штатный backup PostgreSQL и сохранённых конфигураций по
   `docs/server-platform/OPERATIONS.md` и `MIGRATION-STATUS.md` в корне репозитория.
2. В новом release checkout выполнить `git fetch origin`, `git switch with-tablet`,
   сверить commit. Не выполнять `reset --hard` в рабочем release.
3. В `server` выполнить `npm ci`, `npm run prisma:generate`.
4. В окружении сервера задать постоянный случайный секрет `LOADER_OFFLINE_PLAN_KEY`
   (например, вывод `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`).
   Хранить его вместе с серверными секретами вне Git, включить в защищённый backup.
   При отсутствии отдельного ключа используется существующий `JWT_SECRET`.
   Если нет обоих, автономные токены не выдаются. После выбора ключ не менять
   без плана обработки неотправленных заданий.
5. На изолированном стенде прогнать:

   ```bash
   node scripts/loader-tasks-test.mjs
   node scripts/loader-terminals-test.mjs
   node scripts/with-tablet-test.mjs
   npm run test:host-current
   ```

6. Переключить release и перезапустить процесс по действующей PostgreSQL-инструкции
   эксплуатации. Не использовать старые SQLite deploy-команды. Проверить health,
   вход планшета, получение offlineToken, новый `/api/loader/weight` и журнал.
7. Затем установить новую Pi и APK; выполнить полевой checklist из
   `malina_for_korovki/WITH_TABLET.md`.

HTTP-тест автономных заданий использует отдельную SQLite `:memory:` как тестовую
реализацию хранилища. Production-адаптер PostgreSQL не меняет схему и использует
тот же reducer, однако end-to-end проверка новой функции на PostgreSQL должна
быть выполнена на отдельной тестовой БД перед переключением release.

## Контракт Pi

В существующую host-телеметрию добавлено поле:

```json
{"scale_measurement":{"version":1,"deviceId":"Hozain_01","packetId":"boot:123","timestampMs":1800000000000,"weightKg":560,"valid":true,"calibrationId":"revision"}}
```

Это тот же объект, который выдаёт Pi по LAN `/v1/weight` (возраст LAN может быть
дополнительным полем). Частота телеметрии новой конфигурации Pi 0.5 с. На сервере
сохраняется rawPayload как для принятых inbox-пакетов, так и для обработанных.
Историческая досылка не меняет timestamp самого измерения. Проверить реальную
нагрузку 2 Гц на стенде; предыдущая проверка платформы проводилась при HOST 1 Гц.

При откате сервера прекратится приём новых автономных задач: сначала синхронизировать
планшет или оставить новый обработчик доступным до завершения очереди. Не удалять
приложение/локальную SQLite для устранения конфликтов.

Реальный переход через VPN подтверждён; свежий физический вес и проверка полевого reader остаются отдельной аппаратной приёмкой.

## Удалённое обслуживание планшетов

26.09.2026 добавлены `/api/loader/remote/poll` и `/remote/result` (только ключ терминала), а также `/api/loader/terminals/:id/remote` и `/screenshot` (сайт, только владелец/администратор, не отозванный терминал). UI находится в `frontend/loader-terminals.html`. Команда снимка либо обновления сохраняется в приватном каталоге `server/private-terminal-remote` атомарной заменой JSON; один активный запрос на планшет, срок 24 часа. Включать каталог в резервную копию и переносить при смене release; `LOADER_REMOTE_DIR` может задавать постоянное место. Не публиковать его через nginx. Файлы 0600, каталог 0700; снимки доступны только через проверку прав.

Android опрашивает сервер раз в 10 секунд. Снимается только рабочий WebView, без PIN/логина и других приложений. APK берётся с фиксированного HTTPS-адреса, подпись/пакет/большая версия проверяются на устройстве. Обновление ждёт завершения задания. Результат установки переживает перезапуск приложения. Сервер хранит только последнюю команду и последний снимок; это обслуживание по запросу, не постоянная видеозапись.

Проверка: `node scripts/terminal-remote-test.mjs` — доступ владельца, запрет чужому пользователю и ключу планшета на управленческие маршруты, запрет JWT на poll, валидация PNG, восстановление очереди, статусы, изоляция ID. `loader-terminals-test` проходит после добавления маршрутов. Реальный снимок получен от RugKing и виден в браузере на странице планшетов.
# 27.09.2026 — единый вес Pi

Legacy фильтр остаётся для старых приборов без scale_measurement.
