## Расчёт без постобработки

Основа границ и автоматических сегментов — прежний `module-3/telemetryProcessor.js`. Его FSM не заменена: сохранены движение, debounce, overlap loading/barn, выгрузка и остаток. RTK не разрешает начало замеса вместо HOST. Режим включается `BATCH_PROCESSING_MODE=realtime`, новые замесы имеют `processingMode=realtime-v1`; по умолчанию сохраняется legacy для совместимости.

Для заданий планшета параллельно работает онлайн-проверка `realtime-ingredient-verification.js`. Она получает независимые HOST-пакеты: собственную исходную массу и конечное плато из короткого причинного окна до соответствующей временной границы. Поля `reading.weightKg` планшета не используются для вычисления веса алгоритма. График показывает исходный packet weight без такого сглаживания. Границы шагов служат для сопоставления двух результатов, корм сначала определяется по GPS.

- Подтверждение планшета сразу атомарно сохраняет имя, вес, план и времена шага вместе с событием. Повторы идемпотентны. Автоматические сегменты не дублируют эти факты.
- Независимые название/вес сохраняются в `algorithmIngredientName`/`algorithmWeight`. Проверка использует уже полученные измерения. При короткой гонке между событием и HOST следующий пакет завершает ожидающую проверку; будущие пакеты не пересчитывают готовый результат.
- Однозначная свежая позиция погрузчика имеет приоритет над названием планшета. Для поездок между кучами используется отдельное состояние существующего RTK scoreboard с dwell/entry/heading; оно не вмешивается в HOST-first FSM.
- Без подтверждения погрузчика, если HOST рядом с соломой/люцерной, планшет может подсказать название только внутри этой неоднозначной пары. Сохраняется `low_confidence / pair_tablet_hint`. Колебания GPS между обеими зонами не доказывают смешение кормов. Вне пары планшет не переименовывает определённый GPS компонент.
- `REALTIME_RTK_MODE=auto` автоматически использует подходящие свежие данные; при их отсутствии работает HOST и ограниченная подсказка пары. `disabled` остаётся явным диагностическим режимом.
- Перезапуск восстанавливает FSM, накопленные GPS/весовые сведения и незавершённые проверки из AppState. Смена калибровки не превращается в загрузку/выгрузку; новая явная исходная точка шага возобновляет расчёт. Завершённые факты не заменяются.
- Отменённые нулевые попытки не создают пропуски кормов: их пустые строки убираются, журнал задания остаётся для диагностики. Ненулевые факты сохраняются. Undo и веб-исправления остаются явными действиями.
- Завершение, карточка и отчёты читают сохранённые факты. Обычная обработка не вызывает старый детектор ступенек и не меняет состав замеса. Панель постобработки скрыта в онлайн-карточке; отдельный admin/lab preview остаётся непостоянным сравнением и не пишет в БД.

## Нарушения

Порог — строго больше 10% от плана; ровно 10% допустимо, дополнительного минимального порога в килограммах нет. Подписанный план планшетного шага фиксирован.

| Источник | Результат |
|---|---|
| Планшет подтвердил отклонение >10%, независимо от алгоритма | Красное `TABLET_DEVIATION`, source=tablet |
| Отклонение только у алгоритма, планшет в допуске или не подтвердил | Жёлтое `ALGORITHM_DEVIATION`, source=algorithm |
| GPS устойчиво определил другой доминирующий корм | Жёлтое `ALGORITHM_INGREDIENT_MISMATCH` |
| После завершения отсутствует плановый компонент | Красное `MISSING_COMPONENT`, source=system |
| Загружен компонент вне плана, в том числе неизвестный | Красное `EXTRA_COMPONENT`, source=tablet/system |
| Нарушен относительный порядок загруженных плановых компонентов | Красное `ORDER_MISMATCH`, source=system |
| После выгрузки остался вес | Красное `LEFTOVER_WEIGHT`, category=LEFTOVER |
| Оба результата в допуске | Нарушения нет |
| Только неуверенная солома/люцерна, вес в допуске | Нарушения нет; пометка низкой уверенности у компонента |

Подтверждённое планшетом отклонение соломы/люцерны также красное: низкая уверенность GPS не скрывает известное отклонение веса. Цвета одинаковы в списке замесов, карточке, текущем замесе и отчётах/журнале. При расхождении двух оценок, каждая из которых в пределах плана, бизнес-нарушение не создаётся. Дата нарушения относится к замесу, а не к дате локального прогона.

## Проверка веса и компактный интерфейс — 2026-10-02

Согласие независимого HOST-веса с планшетным фактом использует два настраиваемых допуска: расхождение строго меньше заданного процента либо не больше минимального допуска в килограммах подтверждает вес. Значения по умолчанию — 5% и 5 кг; поэтому 40/45 кг подтверждается по минимальному допуску, а 200/210 кг остаётся расхождением по строгой процентной границе. Порог бизнес-нарушения не изменён: отклонение рабочего факта от плана должно быть строго больше 10%. При подтверждении рабочим фактом становится независимый вес алгоритма; исходный планшетный вес остаётся в БД неизменным и передаётся отдельно как `tabletWeight`.

Оба допуска доступны ADMIN в «Админ панель → Телеметрия → Настройки телеметрии»: `Алгоритм ↔ планшет, %` и `Алгоритм ↔ планшет, минимум кг`. Серверные поля — `tabletAlgorithmWeightTolerancePercent` и `tabletAlgorithmWeightToleranceMinKg`; PostgreSQL/SQLite миграция `20261002000100_realtime_weight_tolerance_settings`. Миграция применена только к локальной рабочей БД `farm_realtime_verified_20261001`, где установлены значения 5/5.

Список и карточка замеса показывают независимые сигналы:

- зелёная галочка — расхождение укладывается в настроенный процентный или минимальный килограммовый допуск, в расчётах принят вес алгоритма;
- жёлтый знак — расхождение веса, другой определённый компонент либо низкая уверенность GPS;
- красный знак — рабочий факт отклонился от плана больше чем на 10%;
- при подтверждении вес алгоритма выводится один раз как `факт / план`; вне обоих допусков рабочим остаётся планшетный факт и отдельно показаны оба веса;
- при расхождении названия прямо показан компонент, который определил алгоритм, без повторения совпавшего веса.

У каждого значка есть `title` и доступная подпись для наведения курсора и клавиатурного фокуса. Одинаковые автоматические и планшетные строки одного компонента не суммируются дважды. ## Структурные нарушения и аудит старой логики — 2026-10-02

В realtime был найден регресс: ранний выход в новой ветке пересчёта сохранял отклонения веса и GPS, но обходил старые проверки состава и порядка. Восстановлены три критичных правила: отсутствующий плановый компонент, лишний/неизвестный компонент и инверсия порядка. Пропуск создаётся только после завершения замеса; лишний компонент и уже доказанная инверсия могут быть показаны сразу. Один и тот же факт не переписывается ради нарушения.

Старая матрица проверена полностью:

- недовложение/перевложение сохранено новой двухисточниковой схемой: `TABLET_DEVIATION` красное, `ALGORITHM_DEVIATION` жёлтое;
- отсутствие, лишний или неизвестный компонент и порядок восстановлены отдельными красными кодами;
- `LEFTOVER_WEIGHT` по-прежнему создаётся старой FSM при завершении выгрузки; бизнес-пересчёт теперь сохраняет общий флаг замеса, если активен остаток;
- старые специальные `STRAW_ALFALFA_TOTAL_MISMATCH`/`STRAW_ALFALFA_RATIO_MISMATCH` не дублируются для realtime с подтверждёнными шагами: отклонение каждого выбранного на планшете компонента больше 10% уже даёт красное нарушение. Если вес в плане, а без RTK нельзя различить пару, остаётся только низкая уверенность согласно принятой логике;
- предупреждения качества телеметрии остаются техническим контуром и не являются нарушениями рецепта.

Проверка рабочей локальной БД нашла 13 структурных записей в 6 из 22 завершённых realtime-замесов и синхронизировала только производный журнал/флаги. `BatchIngredient` сохранил 1746 строк и сумму 722250 кг. У №1385 теперь есть `MISSING_COMPONENT` для люцерны 450/0 кг и `ORDER_MISMATCH` для комбикорма: плановая позиция №2, фактическая №3. Исправлено округление позиций как веса, из-за которого журнал показывал №5.

В интерфейсе критичность компонента отделена от корректности его веса. `ORDER_MISMATCH` показывается отдельной красной пиктограммой порядка с tooltip о плановой и фактической последовательности, но не окрашивает `факт / план` красным. Красный вес оставлен только для `TABLET_DEVIATION`, `MISSING_COMPONENT` и `EXTRA_COMPONENT`. Для №1385 проверено: комбикорм 275/280 кг отображается обычным цветом, рядом одновременно видны значок порядка и зелёное подтверждение веса.

## Обе планшетные границы на графике — 2026-10-02

`tabletMarkers` теперь содержит не только `LoaderTaskEvent.begin`, но и `confirm`: начало и конец берутся по `event.at`, то есть по времени фактического нажатия на планшете, независимо от расчётного интервала компонента. Начало рисуется фиолетовой линией с длинным пунктиром и меткой `Н`, конец — бирюзовой линией с коротким пунктиром и меткой `К`; легенда содержит явные подписи «Начало/Конец: компонент».

Если `BatchIngredient` содержит `tabletTaskId`, API выбирает только связанные задания и не показывает отменённые попытки того же устройства из окна ±3 минуты. Fallback по устройству и временному окну сохранён для старых замесов без постоянной связи. На локальной PG-копии №1373 возвращает 4 начала и 4 конца; №1385 — 3 завершённые пары без лишней отменённой попытки. ## Граница подтверждения и проезд через другие зоны — 2026-10-02

Удалена недостоверная эвристика `mixed_components`. Она распределяла положительные колебания веса по GPS-зонам на всём интервале `begin`→`confirm` и могла принять перевозку уже загруженного компонента через соседнюю зону за дополнительную загрузку. Настоящее расхождение компонента создаётся, только когда доминирующее алгоритмическое название отличается от планшетного. `MISSING_COMPONENT` и `EXTRA_COMPONENT` продолжают отдельно контролировать состав.
