> Обновление: перенос серверных данных и очередей на PostgreSQL выполнен 20 сентября 2026. Фактическое состояние, ограничения и восстановление описаны в [MIGRATION-STATUS.md](./MIGRATION-STATUS.md). Ниже сохранён первоначальный проект; он включает ещё не реализованные этапы.

Аудит 12 сентября 2026. Это план и оценка рисков, не выполненная миграция.

Обновление по уточнениям пользователя: основной объём теперь описан в ARCHITECTURE.md — до 3 хозяйств, 20 устройств, 20 пользователей, HOST 1 Гц и планшетное чтение 2 Гц. Raspberry Pi не менять. Локальный сайт после аудита обновлён fast-forward до `ae052d1`; создана отдельная ветка `refactor/server-platform-postgres`. Сведения о первоначальном HEAD ниже описывают начало аудита.

## Решение

Рекомендую PostgreSQL 18 с актуальным исправляющим релизом. На дату проверки официальный сайт указывает 18.6. Сохраняем Express и Prisma; серверную историю, задания, настройки и очереди постепенно объединяем в PostgreSQL. SQLite на Raspberry Pi сохраняем для автономной доставки при пропадании сети. Не подключаем устройства прямо к PostgreSQL: существующий HTTP-протокол остаётся границей системы.

Основание: у системы одновременно работают приём телеметрии, историческая досылка, расчёт замесов, пользовательские изменения и задания погрузчика. PostgreSQL позволяет конкурентные транзакции и обычное чтение при записи благодаря MVCC. Он не исправляет порядок пакетов и алгоритмические ошибки пересчёта сам по себе. [MVCC](https://www.postgresql.org/docs/18/mvcc-intro.html), [версии и поддержка](https://www.postgresql.org/support/versioning/).

MongoDB потребовал бы переделки связной модели без очевидного выигрыша. Другой SQLite-сервис не снимает зависимость приложения от одного писателя. Обычного PostgreSQL достаточно как исходной архитектуры; отдельные Kafka, Redis, TimescaleDB, PostGIS и кластер не требуются для первого перехода. Нужность расширений и партиционирования решать по измерениям, а не добавлять их в критическое переключение.

## Какие проблемы уже были

1. 16–17 июля: replay, HOST-транзакции и RTK worker одновременно писали в SQLite. Prisma возвращала P1008/P2028, nginx — 504; БД оставалась целой. Простая проверка replayRunning пропускала уже начатые запросы. Добавили drain, mutex и durable inbox.
2. 18 июля: приоритетные live-строки старых batch последовательно сдвигали текущую карту с задержкой до 1 ч 20 мин. Это ошибка выбора пакета, не повреждение SQLite. Исправили выбор newest-live и указатель DeviceCurrentTelemetry.
3. 10 августа: накопившийся за replay хвост после resume превращался в новый исторический хвост и запускал следующий replay. Добавили дневной пересчёт, dirty version/CAS и расширяемый FIFO catch-up fence. Зафиксирован production day replay за 11,3 секунды и отсутствие повторного цикла после исправления.
4. 22 августа: timestamp HOST без зоны интерпретировался как MSK вместо UTC; исправлены 16582 строки со сдвигом 3 часа. Это отдельный риск нормализации времени, который нельзя заново внести импортом.

Источники этих инцидентов — датированные записи AGENTS, а не свежие production-логи. Подтверждения, что сейчас сайт снова падает именно по этим причинам, нет.

## Полный состав переносимых данных

| Хранилище | Содержимое | Решение |
|---|---|---|
| Main SQLite, Prisma | Телеметрия, current pointer, замесы, компоненты, нарушения, предупреждения, пользователи, рационы, зоны, группы, настройки и события | PostgreSQL на первом этапе |
| Main SQLite, таблица AppState вне Prisma | Граница очистки HOST-трека | Явно включить в схему и импорт |
| host-ingress.sqlite3 | HOST inbox, dedupe, live-флаги, meta, dirty days, version, replay/catch-up state | Сначала сохранить, затем перенести в PG без изменения семантики |
| rtk-ingress.sqlite3 | RTK inbox, hash, retry/permanent/processed | Аналогично HOST; сохранить raw bytes и hashes |
| loader-tasks.sqlite3 в origin/main | LoaderTask, LoaderTaskEvent, LoaderTerminal | Перенести вместе с бизнес-данными; их нет в Prisma schema |
| rtk-ingest-dead-letter.jsonl и прочий runtime/config | Неразобранные запросы, параметры среды | Архивировать отдельно и сверить |
| SQLite Raspberry Pi | Буфер и идентичность stream/packet | Оставить на устройстве |

Недостаточно экспортировать только Prisma-модели или только `dev.db`. Для общего согласованного финального снимка остановить все серверные писатели, в том числе приём запросов, loader и schedulers. Отдельные online backups файлов сами по себе не обеспечивают общей атомарной точки между четырьмя БД.

## Конкретные изменения кода

1. `server/prisma/schema.prisma`: provider PostgreSQL, явная стратегия timestamp и идентификаторов; добавить AppState и новые серверные таблицы. Создать отдельную начальную PG-миграцию. SQLite SQL-миграции и `_prisma_migrations` не импортировать как применённую историю PG. Старую историю сохранить в Git/архиве. [Ограничения Prisma Migrate](https://www.prisma.io/docs/orm/v6/prisma-migrate/understanding-prisma-migrate/limitations-and-known-issues).
2. `src/database.js`, `scripts/replay-batches-from-telemetry.mjs`, maintenance scheduler: убрать SQLite PRAGMA/sequence SQL из PG-пути. `VACUUM` в PG имеет другую эксплуатационную модель; включить и наблюдать autovacuum.
3. `/admin/replay-days` в `telemetry.routes.js`: переписать `strftime(timestamp / 1000, ..., '+7 hours')` для PostgreSQL. Абсолютное время хранить UTC, предпочтительно `timestamptz(3)`, farm day вычислять в Asia/Barnaul. Импортировать сохранённый timestamp, не пересчитывать историю из raw заново.
4. `track-state-store.js`: вместо runtime CREATE TABLE и некавыченных CamelCase использовать миграцию/Prisma либо корректно цитированный SQL. PostgreSQL иначе приводит имена к нижнему регистру.
5. `host-ingress-store.js`, `rtk-ingress-store.js`, loader stores: синхронный better-sqlite3 API заменить асинхронным PG-кодом; обновить все вызывающие routes/workers/current/health. Наивная замена подключения оставит часть данных в SQLite.
6. Loader: сохранить UUID, ownerId, state, canonical event payload, revision, keyHash, passwordVersion, revokedAt. Пароль пользователя импортировать побайтно, не перехешировать: иначе терминалы инвалидируются. Сохранить частичный UNIQUE для одного ready/active задания на deviceId и UNIQUE(taskId,revision). В apply добавить блокировку строки задания или атомарный CAS по revision; SQLite ранее не позволял двум писателям одновременно пройти эту логику.
7. Очереди: ACK/202 только после durable commit. claim с транзакцией и lease/временем истечения, а не сброс всех processing при старте любого процесса. Сохранить idempotency HOST(device,stream,packet), RTK ingestKey/request_hash и ответы acked_packet_ids. При сбое после commit и до ACK повторный запрос не должен создавать второй факт.
8. Согласованность расчёта: сначала оставить один worker и существующее исключение replay/live. Затем ввести координацию в БД по устройству и пересекающемуся диапазону расчёта. Процессный TelemetryWriteCoordinator не защищает от второго PM2-процесса; schedulers сейчас запускаются из index.js в каждом экземпляре. RTK влияет на HOST через effective position, поэтому нельзя независимо распараллелить связанные потоки без общего порядка.
9. Для масштаба: расчёт вне длинной пишущей транзакции на зафиксированном входе, сохранение во временное поколение, затем короткая атомарная публикация с проверкой dirty version. Учитывать изменения справочников и ручные изменения нарушений во время вычисления. Это отдельная доработка после переноса, а не обязательное условие первой репетиции.
10. Перенести DB-интеграционные тесты с SQLite-копий на изолированный PostgreSQL. SQLite unit-тесты сохранять для оставшихся локальных очередей. Зафиксировать совместимые версии Prisma CLI/client; аудит выявил также SQLite adapter 7.x рядом с client 6.x в декларации зависимостей — проверить реально используемые версии, не совмещать перенос с бесконтрольным обновлением всех пакетов.

## Что может сломаться

| Риск | Контроль |
|---|---|
| Пропущены runtime-таблицы или очередь принятых пакетов | Полная инвентаризация реального сервера, снимок всех файлов, сверка pending/retry/permanent и meta |
| Сдвиг UTC, другой день замеса | Типизированный импорт epoch milliseconds, сравнение min/max и значений по ID, сценарии полуночи и 21–22 августа |
| INTEGER теряет диапазон | Для telemetry/inbox IDs и packet IDs рассмотреть bigint сразу; PostgreSQL integer ограничен 2147483647. API должен явно сериализовать BigInt, фронтенд — не терять точность |
| После импорта новые ID конфликтуют | Сохранить старые ID/внешние ключи, выставить sequences выше MAX(id). Не сбрасывать общую sequence при дневном replay |
| Реальные строки не соответствуют схеме | Проверить enum, boolean, nullability, orphan FK, диапазоны, нулевые байты/кодировки и JSON; не удалять непрошедшие строки молча |
| Дубли, повторная обработка, ACK без сохранения | Fault injection до/после commit, перед ACK и после main write; проверка постоянных ключей дедупликации |
| Ошибка SQL внутри PG-транзакции | Проверить catch/retry: не продолжать aborted transaction, повторять всю идемпотентную операцию; bounded retry для deadlock/serialization |
| Два активных замеса/задания, рассинхрон FSM | Ограничения БД, блокировки и один worker до отдельной проверки многопроцессности. FSM меняется в памяти до commit — при retry проверить восстановление состояния |
| Переупорядочивание из-за другого query plan | Явный orderBy(timestamp,id); тест позднего пакета, одинаковых timestamps и нескольких устройств |
| Replay стирает комментарии или изменяет номера/ссылки | Импортировать расчётные таблицы как есть, не пересоздавать при переносе; отдельно сравнить day/full replay и ручные статусы |
| Растут RAM, CPU и длительность replay | HOST уже читается страницами, RTK index загружается целиком; ограничить контекст/пагинировать, измерить peak RSS |
| Диск заполнен raw, inbox, WAL или backup | Политика хранения, мониторинг роста и свободного места; не включать старый retention по умолчанию — ранее он удалял raw за пределами 14 дней |
| Второй сервер приложения создаёт вторые scheduler/worker | Отдельные роли api/worker/scheduler и DB lease; не включать PM2 cluster после простой смены БД |
| БД недоступна после переноса inbox в PG | Retryable HTTP, сохранённый буфер устройств, испытание реального клиента; предел буфера устройства измерить |

`FOR UPDATE SKIP LOCKED` подходит для конкурентного claim, но сам по себе не сохраняет последовательность пакетов одного устройства. Нужны ownership/lease по устройству и правило порядка. [SELECT и блокировки](https://www.postgresql.org/docs/18/sql-select.html), [числовые типы](https://www.postgresql.org/docs/18/datatype-numeric.html).

## Запас и эксплуатация

Предварительная стартовая конфигурация для стенда/небольшого production: 4 vCPU, 8 GB RAM, расширяемый SSD от 100 GB и внешнее хранилище backup. Это гипотеза для проверки, не обещание вместимости или достаточности: текущий сервер и реальная интенсивность неизвестны. PostgreSQL можно сначала держать на одном сервере с приложением; отдельный PG-хост упрощает независимое наращивание ресурсов. Одна машина остаётся единой точкой отказа.

Объём оценивать по измеренной PG-копии с индексами, дневному приросту, выбранному сроку хранения, worst-case backlog, WAL и месту на восстановление/перестройку. Например, при непрерывном 1 HOST-пакете/с получаем 31,5 млн строк/год на устройство, при 10 — 315 млн. Это сценарий 24/7, а не текущая измеренная нагрузка. Политика raw-архива нужна независимо от двигателя БД.

Начать с индексов deviceId/timestamp/id на телеметрии по запросам, индексов очередей на ready/next_attempt и проверенных индексов замесов/внешних ключей. Не добавлять все индексы без EXPLAIN и нагрузки. При последующем партиционировании по времени учесть, что уникальность dedupe должна переживать границы партиций; её нельзя случайно ослабить.

Backup: PostgreSQL base backup + непрерывный архив WAL вне VPS, контроль успешности и регулярное восстановление на другом экземпляре. `pg_dump` полезен отдельно, но не заменяет base backup для PITR. Предварительные целевые RPO <= 5 минут и RTO <= 60 минут должны быть подтверждены восстановлением; нулевая потеря при гибели VPS требует другого решения, например синхронной реплики. Локальный commit не равен сохранению на другом сервере. [PITR и эксплуатационные ограничения](https://www.postgresql.org/docs/18/continuous-archiving.html).

Наблюдать: p95 ACK/API, возраст oldest ready, current lag, pending/retry/permanent, replay duration/dirty age, pool wait, lock waits/deadlocks, CPU/RSS, DB/WAL growth, free space, autovacuum и возраст успешного backup.

## Порядок перехода

1. Подтвердить сервер и фактический код/схему. Уточнить: «заморожено» означает остановку работ или отсутствие входящих запросов; отсутствие трафика нельзя предполагать. Зафиксировать все источники записи, частоты и допустимое окно остановки.
2. В отдельной ветке от актуального origin/main подготовить PG-схему, перенос основного хранилища и loader, типизированный повторяемый importer с отчётом и checkpoints. Сохранить SQLite inbox на первом этапе — это уменьшает риск для протокола приёма.
3. На согласованной копии выполнить импорт всех бизнес-таблиц и AppState. Сравнить все строки по первичным ключам, нормализованные значения и побайтные raw/hash/password поля; одних counts недостаточно. Сверить внешние ключи, ID и sequences. Зафиксировать длительность и занимаемое место.
4. На PostgreSQL выполнить тесты API, current, timezone, loader, replay, поздних пакетов и отказов. Убедиться, что все сетевые отправки (digest и т.п.) отключены на стенде. Отдельно проверить рестарт workers и перегрузку досылкой.
5. Первый production cutover: закрыть все записи, остановить workers/schedulers, получить финальные согласованные копии main/inbox/loader и config, импортировать финальные данные и сверить. Сохранить прежние код и файлы. Запустить PG-версию сначала закрытой для внешних записей, выполнить контроль; затем открыть трафик.
6. Наблюдать полный рабочий цикл и реальную выгрузку накопленного буфера. Инструменты диагностики и backup уже должны работать. Нагрузочный тест: не менее 10x измеренного штатного пика, параллельно replay и типовые чтения; backlog после прекращения всплеска должен убывать, а current не уходить назад. Проектные стартовые цели: ACK p95 < 200 мс, обычный API p95 < 500 мс; окончательные SLO уточнить на реальном оборудовании.
7. Второй этап: перенос серверных inbox/meta/dirty в PG после проверки crash/retry/FIFO семантики. Копировать состояния очереди под остановкой, сверять числа и hashes; не пересчитывать dedupe из заново сериализованного raw. В конечном серверном варианте четыре SQLite-файла больше не являются рабочим хранилищем.
8. Отдельно оптимизировать replay и разрешать несколько workers. До этого обещание «можно просто запустить несколько копий сайта» неверно.

### Откат

До открытия внешних записей: вернуть прежний код и согласованный комплект SQLite-файлов, включая inbox/loader/meta; это простой откат.

После первой новой записи в PG: старый SQLite уже отстал. Простое переключение DATABASE_URL потеряет новые изменения. Нужны остановка записей и заранее испытанный экспорт дельты всех изменённых данных (не только телеметрии: задания, пользователи, ручные правки и очередь) либо исправление вперёд на PG. Отсутствие готового переноса дельты означает отсутствие быстрого отката после открытия трафика. Эту границу явно включить в runbook; архив старой БД её не устраняет.

## Оценка работ

Предварительно для одного разработчика: 3–5 рабочих дней на main/loader, importer и совместимость, 2–4 на репетицию/отказные тесты/backup/cutover; ещё 3–5 на полное перемещение серверных очередей. Итого ориентир 8–14 рабочих дней при доступном сервере и данных без неожиданных дефектов. Оптимизация архитектуры replay и многопроцессность оцениваются отдельно. Время реального простоя определяется только репетицией на свежей копии; сейчас его нельзя честно назвать.

Критерий готовности: подтверждена полнота данных и работа прикладных сценариев на PG, нет потери подтверждённых пакетов в fault tests, очередь восстанавливается после restart, нет replay-loop, проверено восстановление backup и есть согласованный план после границы отката.
