# Эксплуатация PostgreSQL

## Границы выпуска

Один экземпляр приложения обслуживает одну БД хозяйства. Бизнес-данные, HOST/RTK inbox, метаданные replay и checkpoint расчёта сохраняются в PostgreSQL. Процесс подтверждает приём только после COMMIT inbox. Обработка использует leases, heartbeat, повторные попытки и дедупликацию. Один расчётный процесс на БД защищён PostgreSQL advisory lock; при потере соединения владельца процесс завершается и PM2 поднимает его заново.

Нельзя запускать второй расчётный worker того же хозяйства или рассчитывать на PM2 cluster mode: FSM и часть координации остаются в одном процессе. API и workers допускают отдельные флаги запуска, но независимое горизонтальное масштабирование расчёта этим выпуском не заявляется. Для нового хозяйства нужны отдельные database/role и доверенная маршрутизация доступа; общий каталог пользователей/хозяйств пока не реализован.

## Установка исходников

Node.js 22; точная рабочая версия и Git commit указаны в MIGRATION-STATUS.md. В server выполнить `npm ci`, `npm run prisma:generate`. Генерируются клиенты SQLite (для миграции/фикстур) и PostgreSQL. Для рабочего процесса задать ограниченный DATABASE_URL и `INGRESS_BACKEND=postgres`. SQLite-пути из старого .env не определяют активный backend при этом переключателе.

`npm run migrate:postgres` выполнять с административным подключением. Приложению выдавать SELECT/INSERT/UPDATE/DELETE на прикладные таблицы, USAGE/SELECT на sequences; роль не должна иметь SUPERUSER/CREATEDB/CREATEROLE. Административный DATABASE_URL не передавать PM2.

## Перенос очередей

1. Создать полный комплект backup кода, конфигурации и согласованных данных; проверить SHA-256, восстановить dump в отдельную БД. Скопировать комплект вне VPS.
2. Подготовить новый release отдельно от рабочего, установить зависимости и генерировать клиенты. Применить добавочные PG migrations.
3. Остановить прежний приём и обработчики. Сделать SQLite backup API для обоих остановленных inbox (нельзя копировать один .sqlite3 без учёта WAL).
4. Запустить `import-ingress-postgres.mjs` с IMPORT_POSTGRES_CONFIRM, IMPORT_SQLITE_HOST, IMPORT_SQLITE_RTK и IMPORT_REPORT_PATH. Импортёр требует пустые целевые inbox, проверяет все столбцы/счётчики/хеши одной транзакцией. Прерванные processing переводятся в retry, старые permanent и dirty дни сохраняются.
5. Запустить новый release с ограниченной ролью на свободном loopback-порту, проверить health и авторизованные API. Затем переключить nginx, проверить nginx -t, публичный HTTPS и старый порт устройств 3000.
6. Сохранить PM2, обновить systemd backup, выполнить online backup и полное проверочное восстановление. Старые release и SQLite сохранить.

До открытия нового приёма можно остановить новый процесс и вернуть прежний backend: основная PG schema меняется добавочно. После первого нового ACK нельзя просто включать старые SQLite inbox: новые подтверждённые пакеты находятся в PG. Нужен forward fix либо контролируемое сохранение и перенос всех новых данных; старый dump не восстанавливать поверх рабочего автоматически.

## Резервирование и восстановление

Шаблоны `server/ops/farm-platform-backup.service` и `.timer` используют закрытый EnvironmentFile администратора. Для полностью PG backend задать BACKUP_INGRESS_BACKEND=postgres: backup экспортирует единый snapshot и выполняет pg_dump без остановки приложения. Manifest включает счётчики всех таблиц и SHA-256, архив содержит код и приватную серверную конфигурацию. Такие архивы хранить с правами 0600/0700, не добавлять в Git и не публиковать.

`verify-postgres-backup.mjs` требует BACKUP_DIRECTORY и новый RESTORE_DATABASE с префиксом farm_restore_. Скрипт проверяет файлы, восстанавливает dump в отдельную БД, сверяет все счётчики и constraints, записывает restore-verification.json; только успешно проверенную временную БД удаляет. Он не переключает рабочий сайт.

При аварии восстановить выбранный dump в новую БД, выдать отдельную ограниченную роль, развернуть соответствующий release и секреты, проверить API и только затем переключать nginx. Очередь может содержать processing: lease истечёт и пакет повторится; расчёт восстанавливается из checkpoint. Изменение версии Node/V8 требует проверки чтения checkpoint и восстановительного теста до обновления.

Хранятся семь ежедневных наборов. Это не PITR и не репликация. Автоматическая ежедневная копия на том же VPS не защищает от потери VPS; ручные проверенные копии на рабочем компьютере перечислены в MIGRATION-STATUS.md. Для автоматического внешнего хранения нужен отдельный доступный storage и его credentials.

## Пулы соединений

Рабочий процесс: Prisma API 12 + расчёт 4, pg API 6 + worker 2, максимум 24 подключения (session lock входит в API pg pool). PG max_connections=50. Выделенные пулы выбираются async context; это та же БД, не отдельная копия данных. При добавлении хозяйств пересчитать общий бюджет с запасом для backup/администрирования; три процесса с текущими максимумами превышают лимит.

## Ёмкость и наблюдение

Следить за pending/retry/processing, oldestPendingAgeSeconds, permanent, последней ошибкой, HTTP задержками, рестартами PM2, успехом backup timer и свободным диском. Рост возраста очереди при постоянной нагрузке требует расследования, даже если ACK быстрый. 113 старых permanent RTK сохранены как исторические ошибки, а не потеря миграции.

20 HOST по 1 Гц дают 1 728 000 пакетов/сутки; чтение 20 планшетов по 2 Гц — 40 запросов/с. Это требует планирования диска независимо от выбора БД. Raw retention намеренно не включён: полная история сохраняется. До подключения всех 20 устройств измерить размер суток реальных пакетов и увеличить диск/настроить согласованный архив; имеющийся VPS не является бессрочным хранилищем. Смена БД не устраняет отказ единственного VPS.

Нагрузочные тесты запускаются только в явно разрешённой тестовой БД. Синтетические устройства в production не создавать. Raspberry Pi и её протокол не менять.
