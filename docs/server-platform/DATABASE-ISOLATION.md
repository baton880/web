# Изоляция хозяйств: один домен и отдельные БД

> Обновление: первый этап переноса уже выполнен. Фактическое состояние, ограничения и восстановление описаны в [MIGRATION-STATUS.md](./MIGRATION-STATUS.md). Ниже сохранён первоначальный проект; он включает ещё не реализованные этапы.

Уточнение 2026-09-12 после обсуждения ARCHITECTURE.md. Пользователь рассматривает раздельные БД при общем vi-korm.ru. Первоначальное предложение общей БД с farmId не является обязательным и не утверждено. Для 2–3 независимых хозяйств предлагается следующий вариант для дальнейшего проектирования.

## Рекомендуемый вариант

Один код и единый выпуск приложения; общий вход vi-korm.ru; отдельная PostgreSQL database на каждое хозяйство с отдельной ролью и ограниченными правами. Небольшой общий каталог хранит учётные записи, memberships и серверное сопоставление хозяйств с конфигурациями подключения. Пароли подключений хранятся в защищённой серверной конфигурации, не в клиентском запросе. Бизнес-данные, устройства, настройки, jobs и checkpoints каждого хозяйства находятся в его БД.

При входе сервер проверяет членство пользователя; если хозяйств несколько, предлагает выбор. Доверенный tenant context определяет БД. Идентификатор БД/URL подключения из браузера никогда не используется напрямую. Кеши, задания, логи и метрики имеют farm context. Отдельные workers по хозяйствам дают удобную изоляцию для трёх хозяйств и возможность перенести одно из них на другой VPS позднее. Бюджеты соединений и ресурсов задаются отдельно.

Терминалы используют проверенную привязку хозяйства и машины. Для существующей телеметрии сохраняются прежние endpoints и назначение текущему хозяйству; новые источники получают проверяемую привязку. Если старые устройства присылают одинаковые идентификаторы без различимого признака источника, отдельные БД не решают маршрутизацию автоматически. Raspberry Pi не менять.

Общий домен не означает общую базу или один физический сервер. Nginx/gateway может направлять запросы на нужный backend. Нельзя просто указать несколько IP одного домена и ожидать распределения по хозяйствам: выбор должен учитывать доверенный контекст, а не случайный DNS-ответ.

## Сравнение

| Вариант | Плюсы | Цена |
|---|---|---|
| Одна БД, общие таблицы с farmId | Единая миграция, удобные общие отчёты/транзакции | Ошибка tenant-фильтра опаснее; независимое восстановление хозяйства сложнее |
| Отдельные БД в одном PG-кластере | Чётче разделены данные/права, проще логический экспорт и перенос одного хозяйства | Миграции применяются к каждой БД, несколько pools, общие отчёты требуют агрегации |
| Отдельные экземпляры приложения и PG на одном VPS | Раздельный lifecycle и лимиты процессов | Больше ресурсов/эксплуатации, отказ VPS всё ещё общий |
| Отдельный VPS для каждого хозяйства | Разделены ресурсы и отказ машин | Больше серверов, backup/мониторинга/обновлений; общий вход требует gateway или поддоменов |

Отдельные БД одного кластера делят CPU/RAM/диск, WAL и отказ PostgreSQL. Это не HA и не полная изоляция нагрузки. Физический PITR восстанавливает кластер: для отката одной БД ко времени понадобится восстановление в отдельный временный кластер и логический перенос выбранной БД. Для простой независимой выгрузки подходят отдельные pg_dump; они не заменяют PITR.

## Корректировки первоначального плана

- Общие Farm/Membership остаются в каталоге доступа; бизнес-таблицы не обязаны иметь tenant-фильтр при надёжной маршрутизации в отдельные БД. Внутри каждой БД всё равно нужны реестр устройств, отношения и проверки прав.
- Глобальное сопоставление user ID, терминальных ownerId и passwordVersion проектировать явно. Нельзя при переносе терминалов потерять привязку к пользователю или поменять его сохранённый hash.
- Миграции ведутся одним кодом, применяются ко всем хозяйствам с учётом schema version. Нужна совместимость на время последовательного rollout и восстановление при частичном успехе.
- Запрос, транзакция и job работают в заранее выбранной БД. Общий каталог и tenant DB не имеют обычной общей транзакции: provisioning делать повторяемым, с состояниями и восстановлением после ошибки.
- Тест изоляции включает подмену farm context, чужие ID, терминалы, кеш, очередь и поведение при недоступности одной БД. Остальные хозяйства продолжают работать, пока общая инфраструктура исправна.
- Инфраструктуру и копии кода разворачивать автоматически из одного релиза. Отдельные вручную расходящиеся версии сайта для хозяйств не планируются.

Предложение друга «новое хозяйство — новый VPS» технически возможно и совместимо с общим доменом через маршрутизацию. Оно не устраняет дефекты SQLite/replay в каждой копии и не обязательно для текущего масштаба. Общий код с отдельными БД позволяет позднее вынести хозяйство на VPS без изменения пользовательского адреса.

Источники: [PostgreSQL: databases, изоляция и общий WAL](https://www.postgresql.org/docs/18/manage-ag-overview.html), [Nginx reverse proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).
