## Реализованный прототип RTK

`server/src/modules/telemetry/rtk-postgres-ingress-store.js` хранит RTK-запросы в PostgreSQL и сохраняет дедупликацию по SHA-256 исходного raw body. Интерфейс асинхронный; timestamps возвращаются в прежнем ISO-формате. Внутренний ID BIGSERIAL, на границе текущего числового API проверяется Number.isSafeInteger.

Атомарный claim использует UPDATE с SELECT FOR UPDATE SKIP LOCKED. Каждая попытка получает lease_owner, уникальный lease_token и lease_until. Завершение, retry и permanent требуют действующего токена и владельца; истёкший токен не может изменить запись. Конструктор нового процесса не сбрасывает чужие processing. Истёкшие leases можно забрать заново, число попыток сохраняется.

`rtk-ingress-worker.js` теперь ожидает асинхронные операции store и продлевает lease во время долгой работы. Старый синхронный SQLite store совместим через await и продолжает проходить регрессии. На production этот изменённый worker пока не загружался.

Схема прототипа: `server/ops/stage2-rtk-ingress.sql`. Это **не production migration**: использовать только на новой farm_test_* БД. Перед выпуском перенести схему в Prisma migrations/schema и согласовать importer.

## Выполненные тесты

`postgres-rtk-queue-test.mjs`, PostgreSQL database `farm_test_rtk_queue_20260913`:

- 40 одновременных вставок 20 различных запросов создают ровно 20 строк.
- 30 одновременных попыток claim получают 20 различных записей; повторное завершение запрещено.
- Дочерний процесс аварийно завершается после commit enqueue, до возврата результата; повтор не создаёт дубль.
- Дочерний процесс аварийно завершается после claim; новый процесс не сбрасывает действующую lease. После истечения срока запись забирается с новым токеном; прежний владелец отвергается.
- Renewal, retry delay, malformed/permanent, пропуск заблокированной строки, очистка только старых processed.

`postgres-rtk-worker-test.mjs`, финальная database `farm_test_rtk_worker_final_20260913`:

- Обработка дольше первоначальной lease не позволяет конкуренту забрать запись благодаря heartbeat.
- Искусственная ошибка даёт durable retry, затем успешное завершение.
- Искусственная потеря lease во время обработки: старый worker не может завершить или вернуть в retry запись нового владельца.
- Malformed JSON не доходит до обработчика телеметрии; запись permanent, процессная блокировка освобождается.

## HOST: ядро очереди и обработчик проверены на PostgreSQL

Продолжение 13 сентября около 00:13 UTC. Production не переключался. Добавлены `host-postgres-ingress-store.js`, схема стенда `stage2-host-ingress.sql`, тесты `postgres-host-queue-test.mjs` и `postgres-host-worker-test.mjs`.

В PostgreSQL перенесены приём legacy/batch, исходные dedupe/receipt keys, атомарное понижение прежнего live-пакета, current/recent, выдача очереди с lease, high-water, dirty ranges/versions, границы pre/post replay, явное восстановление прерванного пересчёта и очистка processed. Короткие транзакции состояния сериализованы advisory lock на уровне БД хозяйства. Конструктор не сбрасывает состояния других процессов.

`host-ingress-worker.js` адаптирован к async store. Общий `ingress-lease-heartbeat.js` продлевает lease в обоих обработчиках. HOST completion проверяет действующее владение и атомарно сохраняет high-water, dirty/fence и processed. Прикладная запись основной телеметрии всё ещё требует отдельной межпроцессной координации; несколько вычислительных workers не разрешены.

Подтверждено на реальном PostgreSQL:

- Сравнение одинакового сценария с SQLite: receipt/dedupe, causal current, FIFO внутри границы, приоритет нового live за границей, расширение post-replay, переход суток, high-water и сохранение новой dirty generation совпали.
- 30 конкурентных batch-вставок одного потока оставляют один актуальный pending live. 35 конкурентных claim получают ровно 30 различных записей.
- Старый lease не может завершить повторно выданную запись. 20 конкурентных dirty updates сохраняют version=20; очистка throughVersion=19 не удаляет эту запись.
- Ошибка посередине batch insert откатывает все строки и изменения current.
- Явное восстановление прерванного replay продолжает очередь в хронологическом порядке.
- Искусственная ошибка PostgreSQL на финальном UPDATE processed откатывает вместе high-water, dirty generation, fence и статус очереди.
- HOST worker продлевает lease при долгой работе, делает durable retry и передаёт dirty range планировщику только после освобождения границы.
- После передачи lease другому владельцу старый worker не меняет ни очередь, ни replay metadata.

Изолированные БД финальных проверок: `farm_test_host_queue_atomic_20260913`, `farm_test_host_worker_20260913`. RTK повторно проверен после вынесения heartbeat в общий модуль: `farm_test_rtk_worker_shared_20260913`. SQLite `test:replay-safety`, `test:host-ingress`, `test:rtk-ingress` также прошли. Сообщения intentional failure/lease expired в тестах ожидаемы, это специально внесённые сбои.

Полный HTTP/приёмники/main-DB/replay цикл с новыми очередями ещё не подключён. Нагрузочный результат первого этапа нельзя автоматически переносить на этот прототип.

## Что ещё требуется до переключения

1. Ядро HOST и async workers реализованы и проверены. Осталось связать их с настоящими приёмниками/main-DB и планировщиком; восстановление replay разрешать только владельцу исключительного права на расчёт. При импорте старого SQLite отдельно нормализовать исторические некорректные live-флаги, без сброса leases в конструкторе.
2. Адаптировать вызывающие API/current/health/replay методы к async без пропущенных await. Подключение PostgreSQL очередей только явной конфигурацией после полной проверки, без автоматического включения прототипа.
3. Сделать согласованный импорт обеих очередей вместе с meta/dirty, проверить все исходные поля, IDs, permanent/retry и преобразование processing в восстанавливаемое состояние.
4. Добавить PG миграции и ограниченные права приложения. Перепроверить backup/restore после переноса всех очередей, затем убрать паузу приложения из обычного PG backup.
5. Прогнать реальные приёмники HOST/RTK, current API, replay safety и общую нагрузку на восстановленном снимке до нового production cutover.

Lease защищает **переход состояния очереди**, но сама по себе не отменяет уже выполняющийся прикладной расчёт. До межпроцессной координации и fencing бизнес-транзакций нельзя запускать несколько вычислительных workers одного хозяйства. Нынешний процессный TelemetryWriteCoordinator остаётся единственным ограничителем совместных HOST/RTK записей внутри одного процесса.

Регистрация нескольких хозяйств, общий каталог пользователей/маршрутизация БД и реестр связей устройств остаются последующими этапами. Постоянное внешнее хранилище для автоматических копий пока не выбрано.
