Статус 12 сентября 2026 UTC (13 сентября по времени хозяйства). Это отчёт о реально выполненном первом этапе. ARCHITECTURE.md и PLAN.md описывают также последующие, ещё не реализованные этапы.

Сохранены остальные справочники и настройки, IDs, UTC milliseconds, хеши паролей, версии и ключи терминалов. PostgreSQL sequences выставлены с учётом MAX(id) и исторического sqlite_sequence.

Проверено:

- 60-секундный стенд: 20 устройств по 1 пакету/с плюс 20 читателей по 2 запроса/с. Принято и обработано 1200 пакетов, 2400 чтений, ошибок 0. p95 ACK 135 мс, current 232 мс, очередь в конце пуста. Это короткий тест указанного масштаба, не доказательство предельной ёмкости или многосуточной устойчивости.

## Резервные копии

Полные архивы сайта и окружения (исходники, зависимости, Git, БД, .env, /etc, PM2, SSH, конфигурация Amnezia и nginx logs) сделаны **до переноса**. Это прикладной архив с системными настройками, не поблочный образ всего VPS.

1. `/opt/backups/farm-site/platform-transition-20260912/full-application.tar.zst` — первый полный архив, SHA-256 `c6fb7aea22dde0f2e4be11f70dca2522e3c6703bd79938cbfa76d20931be2fff`.
2. `/opt/backups/farm-site/pre-postgres-cutover-20260912/full-application.tar.zst` — свежий полный архив непосредственно перед переносом, SHA-256 `e6389b5f767ae0e5cdad5c5f50f1eb3e9d16678cb5e102a1bb4c5abf27e9f7cc`.
3. В обоих каталогах есть отдельные согласованные SQLite snapshots, SHA256SUMS и metadata. Второй содержит import-report.json с результатами проверки каждой таблицы.
4. Локальные копии и метаданные: `C:\Users\Windows\projects\tmp\server-transition-20260912`. Оба полных архива скачаны; локальные SHA-256 совпали.
5. Проверенная новая копия PG и inbox: `/opt/farm-platform/verified-postgres-backup.tar`, SHA-256 `74cf81e707e6d8816e011b43e87ff20f3234b762112ca96fcb48eaf2637f11b0`. Исходный каталог `/opt/backups/farm-site/pg-daily/2026-09-12T16-58-52-781Z`. Архив скачан на этот компьютер, локальный SHA-256 совпал.

Ежедневное копирование: systemd `farm-platform-backup.timer`, 03:15 Asia/Barnaul (20:15 UTC), последние 7 завершённых ежедневных копий. Полные архивы переноса этим retention не удаляются. Реализация: `server/scripts/backup-postgres-platform.mjs`.

Приложение кратко останавливается; в этот момент экспортируется PG snapshot и снимаются оба SQLite inbox. После этого приложение запускается, а pg_dump использует удерживаемый snapshot. В первом проверенном запуске пауза stop/restart составила 3897 мс; готовность API после запуска добавляет время прогрева. Сеть/устройства должны повторять неподтверждённые запросы. Ночью возможен краткий HTTP 502. После полного перехода inbox на PG эту паузу можно убрать.

Ежедневные копии пока лежат на том же VPS. Автоматическая отправка в независимое хранилище, WAL/PITR и резервный сервер не настроены. Текущая локальная копия защищает точку переноса, но не будущие изменения. Целевой RPO в несколько минут пока не обеспечен.

## Проверка и восстановление

Текущая проверка: `curl -fsS https://vi-korm.ru/api/health`; дополнительно из рабочего server: `node scripts/postgres-production-smoke.mjs`. Для smoke на домене задать `SMOKE_BASE_URL=https://vi-korm.ru`. Использовать настройки приложения, не административное окружение.

Изменения схемы PG применять через `npm run migrate:postgres` с административной конфигурацией. `migrate:db`, старые seed/create-admin/migrate-users и лабораторные SQLite-скрипты не использовать для production PG; они не входят в проверенный путь переноса. Пользователи и терминалы уже импортированы, повторное создание не требуется.

Ручная согласованная копия: `systemctl start farm-platform-backup.service`. Результат: `systemctl status farm-platform-backup.service`, manifest.json и SHA256SUMS внутри pg-daily. Ошибка не должна считаться успешной копией; каталог без manifest.json незавершён.

Проверка restore: в server загрузить защищённый административный DATABASE_URL, задать BACKUP_DIRECTORY конкретной завершённой копии и RESTORE_DATABASE уникальным `farm_restore_*`, запустить `node scripts/verify-postgres-backup.mjs`. Скрипт создаёт только новую проверочную БД, восстанавливает архив с остановкой при ошибке, сверяет строки и ограничения, затем удаляет именно эту временную БД. На ошибке БД оставляется для разбора.

При аварийном восстановлении:

1. Остановить приложение и сохранить повреждённое/текущее состояние отдельно. Выбрать проверенную согласованную копию и сверить SHA256SUMS.
2. Восстановить pg_dump в **новую** БД PostgreSQL, вместе с ролью приложения и её правами. На новом VPS роль создать отдельно: pg_dump одной БД не содержит CREATE ROLE; секреты есть в защищённом конфигурационном архиве.
3. Развернуть исходники и .env выбранного выпуска. Выполнить npm ci и npm run prisma:generate. Восстановить HOST/RTK inbox в новый runtime; не накладывать старые WAL/SHM на файлы из backup.
4. Настроить DATABASE_URL на восстановленную БД; PG порт оставить локальным. Сначала стартовать один экземпляр на закрытом порту с RUN_SCHEDULED_JOBS=false, проверить API и очереди.
5. После сверки переключить nginx, затем включить планировщики, сохранить PM2. Системные units backup восстановить из server/ops и проверить пути.

**Граница отката пройдена:** после публичного переключения нельзя просто вернуть nginx на старый `/opt/farm-server` — новые записи уже могут быть в PG. Без потери данных требуется согласовать дельту или восстановить актуальную согласованную копию; не выполнять обратный импорт молча. Полные replay во время аварийного восстановления не запускать.

## Дальнейшие этапы

1. Перенести HOST/RTK inbox и dirty/retry state в PG с атомарным claim, lease, дедупликацией и crash-тестами. До этого запрещено масштабировать нынешний worker простым `pm2 -i N`.
2. Разделить API и вычисления, обеспечить восстановление состояния расчёта и блокировки replay/live. Нынешние флаги запуска только управляют ролями процесса; межпроцессную безопасность сами не дают.
3. Реестр устройств и их связей; явная маршрутизация 2–3 хозяйств с отдельными БД и проверенным членством пользователей. Сейчас работает одно существующее хозяйство.
4. Длительные тесты роста истории, burst и сбоев, независимый backup storage, контроль диска/ошибок и проверенная процедура потери VPS.
5. До длительной работы 20 устройств определить retention/архивирование и переход telemetry IDs на bigint: сейчас сохранён API-совместимый Int. При 20 строках/с диапазон 32-bit положительных IDs исчерпывается примерно за 3.4 года непрерывной записи; дисковый объём станет ограничением значительно раньше.
